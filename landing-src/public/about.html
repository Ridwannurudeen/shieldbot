How ShieldBot Protects Your Wallet

ShieldBot operates at the transaction layer, not the URL layer. In the browser's page context, before your wallet receives the request, it intercepts transactions (eth_sendTransaction, eth_signTransaction), batches (wallet_sendCalls) and signature requests (eth_signTypedData and its _v1, _v3 and _v4 forms, personal_sign and eth_sign).

How Risk Is Rated

Every transaction receives a risk score before you sign it. Higher means riskier:

0 – 30SAFEThe verdict and details; you can continue
31 – 49!CAUTIONA warning; you choose to proceed or cancel
50 – 70!HIGH RISKA strong warning with threat details
71 – 100BLOCK RECOMMENDEDThe highest risk verdict; blocking is strongly recommended

The extension shows this as a safety score, 100 minus the risk score, so higher is safer there. These are the default bands. A score in the SAFE band is still shown as CAUTION when the risk engine rates the token medium risk or the data is incomplete, and if a check could not run the result is shown as Unknown instead of a number.

Wallet Drainer Protection

A wallet drainer is a malicious smart contract that exploits ERC-20 approval functions or EIP-712 permit signatures to transfer all tokens from a wallet in a single transaction. Standard browser phishing warnings cannot detect these because they operate at the URL layer — the attack happens at the transaction layer.

ShieldBot helps against wallet drainers by:

  • Catching the transaction or signature request before your wallet shows it
  • Analyzing EIP-712 permit and Permit2 signature requests for approval exploits
  • Flagging contracts whose deployer has a history of risky deployments
  • Showing the exact asset change before you sign, when transaction simulation is enabled

Honeypot Detection

A honeypot token allows users to buy but contains hidden code that blocks all sell transactions. The token appears to have liquidity and price action, but holders can never exit.

ShieldBot looks for honeypots in two ways. It simulates a buy and a sell of the token where the chain has a simulator: honeypot.is on Ethereum, BNB Chain and Base, and ShieldBot's own simulation on supported Arbitrum, Robinhood Chain and BOT Chain pool routes. On Arbitrum those are pools pairing the token with WETH on Uniswap V3, Uniswap V2 or SushiSwap. On BOT Chain they are BDEX V2 and V3 pools pairing the token with WBOT. GoPlus token security does not cover BOT Chain. ShieldBot checks GoPlus address labels for the token and, when Blockscout supplies its creator, the creator; a BOT Chain token with no supported BDEX pool reads Unknown for sellability. On the other chains, and for an Arbitrum token with no such pool (for example one traded only on Camelot, or only against stablecoins), it uses GoPlus's honeypot and tax flags instead. It also checks the contract's bytecode for owner powers a honeypot can use, such as a blacklist or a pause switch, which works even for unverified contracts. If a simulation fails, or neither source answers, the result is Unknown rather than Safe.

Pre-Sign Transaction Simulation

When transaction simulation is enabled, ShieldBot sends the transaction to Tenderly for simulation on a copy of the chain state. Tenderly runs it in a sandbox and returns the tokens and amounts that would leave or enter your wallet.

ShieldBot displays this asset delta before the wallet signature dialog appears. For example: "You will send 2.5 BNB and receive 10,000 TOKEN." Tokens the simulation shows leaving your wallet are listed among the danger signals; they do not change the verdict itself. If the transaction reverts in the simulation, the result is incomplete and cannot be SAFE, and a revert on a contract whose own risk score, before community reports and campaign boosts, is already 30 or more is BLOCK RECOMMENDED.

Verdict registries

ShieldBot records verdicts, each with the keccak256 hash of its evidence, in a ShieldBotVerdictRegistry contract that any contract can read. On Robinhood Chain (4663) the registry, a freshness guard and a guarded transfer contract were deployed on 27 September 2026; Telegram scans, guard rescans, and launches it blocks or the guard watches are recorded there. On BOT Chain (677) a verdict registry was deployed on 26 October 2026, at 0xB7cfB87579f232dBa70CDC8Ba063AA7b500D5138, the same address as on Robinhood Chain because the same account deployed both. Telegram /scan and /token results can be recorded in it. A freshness guard and a guarded transfer contract that read it were deployed there on 29 October 2026, at the same addresses as on Robinhood Chain.

The source of all three BOT Chain contracts is verified on BOT Chain's explorer, scan.botchain.ai, since 29 October 2026. The registry's code on BOT Chain is also byte for byte the code of the Robinhood Chain registry, which Sourcify holds as an exact match of its source, and both equal a build of the source in the repository. python -m scripts.check_botchain_registry_code repeats the comparison.
